# 多平台优化

## 触发

- 用户在新聊天中说“对文件夹优化”时，立即使用本技能。
- 用户在新聊天中将“优化”作为独立指令时，立即使用本技能，并结合其提供或随后提供的文件夹继续处理。
- 用户直接提供商品图片数据包文件夹并要求优化、整理或生成优化包时，也立即使用本技能。

## 输入

- 用户提供一个商品图片数据包文件夹。
- 输入文件夹内可能包含 `主图`、`详情页`、`SKU` 三类目录中的任意一种、任意两种或全部三种；`详情` 视为 `详情页` 的有效别名，输出仍统一命名为 `详情页`。
- 三类目录不要求同时存在；只处理实际存在的目录，缺少某类目录不报错，也不阻断其他目录的处理。
- `SKU` 目录名匹配时不区分英文字母大小写。

### 单独类别输入

- 用户直接发送的文件夹本身是 `主图`、`详情页` 或 `SKU` 时，直接处理该类别，不要求外层另有商品数据包目录。
- 自动在该文件夹的同级、上级和下级查找对应商品的款号与名称；优先读取名称带 `-全平台` 且款号一致的文件夹。
- 若输入文件夹的上级目录本身已含可识别款号，则用该款号限制候选，避免匹配到其他商品。
- 找到多个不同款号，或同一款号对应多个不同商品名称而无法唯一判断时，停止并列出候选，不猜测。
- 无法确定款号和名称时明确报告，等待用户提供对应商品路径或名称。
- 单独类别的输出建在输入文件夹同级，名称分别为 `<款号 名称>-sku优化`、`<款号 名称>-主图优化`、`<款号 名称>-详情页优化`。
- 单独类别输出文件夹内直接放该类别原本应有的子目录或单图文件，不再重复建立一层 `SKU`、`主图` 或 `详情页`。
- 单独详情页采用局部改款模式时，优先使用身份识别阶段找到的同款 `-全平台` 文件夹作为原款完整包。

## 输出目录

- 原始输入文件夹只读，不在其中新增、覆盖、移动或删除文件。
- 在输入文件夹的同级目录新建一个输出文件夹，名称为 `<商品名>-全平台-<改款说明>`；无改款说明时为 `<商品名>-全平台`。
- 商品名与改款说明以款号之后的首个半角或全角连字符分隔；保留款号内部的连字符、商品名中的空格及改款说明的顺序。`全平台` 作为独立命名段只出现一次，放在商品名之后；输入名称末尾的 `-优化` 作为处理标记剥离。
- 上述名称适用于完整数据包输入；单独类别输入使用“单独类别输入”规定的 `<款号 名称>-类别优化` 名称。
- 所有优化后的内容写入该输出文件夹，并按输入中实际存在的顶层类别分别建立 `主图`、`详情页`、`SKU` 文件夹。
- 输出中只保留下述指定目录和优化图片，不复制原始尺寸目录或其他内容。
- 若按上述规则命名的输出文件夹已存在，立即停止并报告，不覆盖、合并或删除既有内容。
- 输入文件夹本身已使用目标名称时也停止并报告，原始输入保持只读。

```text
<商品名>-全平台-<改款说明>
├─ 主图                         输入存在主图时创建
│  ├─ 800                    保留输入主图\800
│  ├─ 750                    保留输入主图\750
│  ├─ 1440
│  ├─ 1080
│  ├─ 750正
│  └─ 1920
├─ 详情页                       输入存在详情页时创建
│  ├─ 790
│  ├─ 750
│  └─ 爱库存+蜂享家
└─ SKU                          输入存在 SKU 时创建
   ├─ 通用sku
   │  ├─ 800                   普通结构
   │  └─ 1440                  普通结构
   ├─ 京东
   │  ├─ 1080sku
   │  └─ 1440sku
   └─ 唯品会
```

## 单图简化规则

- 分别递归统计 `主图`、`详情页`、`SKU` 中的源图片数量；三个类别独立判断。
- 某一类别只有一张源图时，保留该类别的顶层文件夹，但取消其下原本要建立的全部子文件夹。
- 将该张源图生成各用途图片，直接放在类别顶层，并把文件名改为原计划的子文件夹名称：

```text
<商品名>-全平台-<改款说明>
├─ 主图
│  ├─ 800.jpg 或 750.jpg       唯一源图来自对应尺寸目录时保留
│  ├─ 1440.jpg                 方图来源时生成
│  ├─ 1080.jpg                 长图来源时生成
│  ├─ 750正.jpg                方图来源时生成
│  └─ 1920.jpg                 长图来源时生成
├─ 详情页
│  ├─ 790.jpg
│  ├─ 750.jpg
│  └─ 爱库存+蜂享家.jpg
└─ SKU
   ├─ 通用sku.jpg
   ├─ 京东.jpg
   └─ 唯品会.jpg
```

- 单图主图按来源类型生成对应用途：`750` 为竖向长图，只生成 `1080.jpg`（`1080×1440px`）、`1920.jpg`（`1440×1920px`）；`800` 为方图，只生成 `1440.jpg`（`1440×1440px`）、`750正.jpg`（`750×750px`）。
- 单张图片直接位于 `主图` 根目录或其他未标记类型的子目录时，按实际像素宽高识别：宽高相等使用方图规则，高大于宽使用长图规则；横图类型无法确定时报告失败。位于 `750`、`800` 来源目录中的图片优先使用目录指定的类型。
- 单图主图若来自输入的 `主图\800` 或 `主图\750`，还要在输出 `主图` 顶层分别保留为 `800.jpg` 或 `750.jpg`；不为不存在的来源虚构原尺寸文件。
- 单图详情页的 `790.jpg`、`750.jpg` 分别等比缩放到 `790px`、`750px` 宽；`爱库存+蜂享家.jpg` 等比缩放到 `790px` 宽。若后者超过 `4800px` 高，按顺序追加为 `爱库存+蜂享家_2.jpg`、`爱库存+蜂享家_3.jpg`。
- 单图 SKU 不再使用多平台的空目录规则；同一张源图分别输出为 `通用sku.jpg`、`京东.jpg`、`唯品会.jpg`。
- 只有图片数量大于一张时，才使用后文规定的多级目录结构。

## 主图处理

多张主图使用输入 `主图` 下的 `800`（方图）和 `750`（竖向长图）目录作为来源，并先在优化包内保留这两个原尺寸目录。只有某一种来源时，仅使用该来源生成对应比例的派生图片；单张主图遵循上文的单图简化规则。

- `主图\800`：保留输入 `主图\800` 内图片的原像素尺寸，统一转换为 JPG 并压缩到 `500KB` 以内。
- `主图\750`：保留输入 `主图\750` 内图片的原像素尺寸，统一转换为 JPG 并压缩到 `500KB` 以内。
- `主图\1440`：将 `主图\800` 内图片调整为 `1440×1440px`。
- `主图\1080`：将 `主图\750` 内图片调整为 `1080×1440px`。
- `主图\750正`：将 `主图\800` 内图片调整为 `750×750px`。
- `主图\1920`：将 `主图\750` 内图片调整为 `1440×1920px`。
- 沿用源图片的基础文件名，输出扩展名统一为 `.jpg`。

## 详情页处理

- 详情来源按以下优先级识别：有图片的 `详情页\790`、有图片的 `详情页\images`、直接放在 `详情页` 根目录中的图片；`images` 匹配不区分英文字母大小写。
- 图片直接位于 `详情页` 根目录时，也视为有效详情来源；在优化包中自动新建对应的 `790`、`750`、`爱库存+蜂享家` 结构后继续处理，原数据包不改动。
- `详情页\790`、`详情页\images` 和 `详情页` 根目录都没有图片时，详情页处理记为失败并明确报错，不从其他未知子目录猜测来源。
- 原数据包中的 `images` 保持不动；若实际来源为 `images`，只在优化包内将其规范命名为 `详情页\790`。
- 将实际选中的详情来源目录内图片等比缩放至 `790px` 宽，输出到 `详情页\790`；高度按原始宽高比计算，不拉伸。
- 将实际选中的详情来源目录内图片等比缩放至 `750px` 宽，输出到 `详情页\750`；高度按原始宽高比计算，不拉伸。
- `详情页\爱库存+蜂享家` 使用同一实际详情来源目录的图片，默认保持源文件顺序和图内从上到下的顺序；下述检测模块前置规则是唯一例外。
- 遇到“检测报告”“科学检测”“安全检测”“抗菌检测”等整块检测说明模块时，必须把该模块放到“模特展示”标题及其全部模特展示图片之前。即使检测模块在源详情或局部改款定位中位于模特展示之后，也要按此规则前置。
- 检测模块移动时必须作为完整模块整体移动，不得切割标题、文字、报告缩略图或同一设计区域；移动后重新分页并检查前后接缝。
- 爱库存+蜂享家详情保持 `790px` 宽，依次合并为长图；单张高度不超过 `4800px`，单个源图超过上限时按高度切分。
- 爱库存+蜂享家详情从 `详情图-01.jpg` 开始连续编号。超过 `20` 张时继续输出并给出警告，不丢弃图片。

### 局部改款详情页

- 当输入 `790` 或 `images` 中提供的是原款详情中修改过的部分切片，而不是完整详情时，启用局部改款模式；修改切片可以为一张或多张，该模式优先于普通详情合并和单图简化规则。
- 处理详情页前必须先判定“完整详情”或“局部改款”，不能看到多张图片就默认按普通规则重新拼接。
- 只要附近能找到同款 `-全平台` 原包，普通模式不得直接生成 `详情图-01.jpg` 等长图。Agent 必须先对照原款完整详情确认输入性质：局部修改时执行覆盖流程；确认为完整详情时才显式使用 `--complete-detail`。
- 输入图片只有原详情中的一部分、文件编号不连续、数量明显少于原款，或画面能对应到原款长图中的局部区域时，一律按局部改款处理。不得把这些修改切片首尾拼接成新的爱库存+蜂享家长图。
- 自动在新数据包的同级目录、上级目录和下级目录中查找名称包含 `-全平台` 的原款式完整交付包。优先选择货号或规范化产品名与新数据包一致的候选。
- 找到多个无法唯一判断的候选时停止并列出路径，不猜测原款包。
- 没有找到时明确告诉用户“未找到原款全平台文件夹”，等待用户提供准确路径后继续；不得用少量改款图生成残缺详情。
- 在原款全平台包内定位 `蜂享家＋爱库存`、`爱库存+蜂享家` 或既有 `akc+蜂享家` 的 `790详情页`，逐张查找包含每个修改切片内容的原款长图。
- Agent 通过画面对照确认每个修改切片所在的原款长图和精确矩形区域，不能只按 `603.jpg`、`612.jpg` 等编号猜测；对应关系不唯一时停止该张替换并请用户确认。
- 复制所有受影响的原款长图作为底稿，将修改切片覆盖到各自对应位置，保留长图中其他未修改区域。
- 只输出实际发生替换的原款长图；未受影响的原款长图不复制到优化包。
- 禁止先复制原款 `790详情页` 整个文件夹再修改。爱库存+蜂享家输出目录必须从空目录开始，只逐张写入替换定位中确认的受影响原图。
- 替换定位 JSON 必须单独列出 `受影响原图`；该集合必须与所有替换项引用的 `原图` 集合完全一致。未发生替换的长图不得列入。
- 输出后必须核对文件名集合：最终爱库存+蜂享家目录中的文件名，必须与受影响原图集合完全一致，多一张或少一张都判定为失败，不得交付。
- 局部改款只有一张修改图时，不创建爱库存+蜂享家子文件夹，结果直接输出为 `详情页\爱库存+蜂享家.jpg`。
- 局部改款有多张修改图时，将改完的原款长图放入 `详情页\爱库存+蜂享家` 文件夹；每张结果图必须保留它在原款 `790详情页` 中的原文件名。
- 局部改款的原始修改图也按相同规则规范输出：单张时生成 `详情页\790.jpg`，多张时按各自原文件名生成到 `详情页\790` 文件夹。
- 多张修改切片落在同一张原款长图时，先在同一底稿上完成全部覆盖，再只输出一张结果图，不重复复制。
- 修改切片覆盖整幅宽度但新旧高度不同时，不拉伸到旧高度；按原图宽度等比缩放新切片，删除旧切片的完整纵向区段并插入新切片，后续内容随高度差自动上移或下移。
- 新图是新增模块、原款中没有对应旧模块时，使用 `插入` 操作，不得为腾出位置而删除相邻原图内容。插入位置必须通过前后画面顺序确认；整宽插入后保留原长图的全部既有内容。
- 插入或替换后单张长图超过 `4800px` 时，按完整详情模块重新分页：优先把末尾的整个模块移到下一张，必要时继续向后顺延，直到每张不超过 `4800px`。
- 分页只能发生在两个完整源模块之间的接缝处，禁止从文字、标题、人物、产品或同一设计模块中间切割。每张结果图都要人工检查上一张末尾与下一张开头的衔接。
- 因重新分页而接收或移出模块的后续长图属于实际受影响页面，应输出；从内容与分页上均完全未变化的长图仍不得复制。
- 所有替换结果统一转换为 JPG，并压缩到每张不超过 `500KB`。

## SKU 处理

- 在输出的 `SKU` 内创建 `通用sku`、`京东`、`唯品会` 三个平台文件夹。
- `通用sku` 按多平台图片处理中的天猫通用 SKU 规则生成：普通结构保留 `800` 和 `1440` 目录；源 SKU 根目录中的图片归入 `800`；已有 `800`、`1440`、`SKU组合` 及其他业务分支保留相对目录。对应尺寸没有图片时保留空目录。
- `京东` 按多平台图片处理规则只创建空的 `1080sku` 和 `1440sku` 目录，不生成 SKU 图片。
- `唯品会` 按多平台图片处理规则保留为空目录，不生成 SKU 图片。

## 图片格式与大小

- 所有输出图片统一为 JPG。
- 每张输出图片必须小于或等于 `500KB`。
- 在不改变规定像素尺寸的前提下逐步降低 JPEG 品质完成压缩，并检查最终文件的格式、尺寸和文件大小。

## 缺失来源与失败处理

- 顶层 `主图`、`详情页`、`SKU` 缺失时跳过该类别，不创建对应顶层输出目录，也不影响其他类别。
- 已存在顶层类别但缺少其所需来源子目录时，创建该类别规定的目录结构，跳过无法生成的图片并给出警告。
- 详情页是例外：存在 `详情页`，但 `790`、`images` 和详情页根目录都没有图片时记为失败并报错；其他类别有可用结果时仍可继续发布。
- 单张图片读取或写出失败时记录失败并继续处理其他图片；可用结果仍然发布，最终状态标记为“部分完成”并列出警告和失败项。

## 执行

首次使用时在 `scripts` 目录运行：

```powershell
uv sync
```

处理数据包：

```powershell
.venv\Scripts\python.exe main.py --source "数据包文件夹路径"
```

- 如果附近存在同款 `-全平台` 原包，脚本会暂停详情页普通处理，防止把改款切片错误拼成长图。
- Agent 对照后确认输入确为完整详情，才使用 `--complete-detail` 继续普通详情生成。

```powershell
.venv\Scripts\python.exe main.py --source "数据包文件夹路径" --complete-detail
```

局部改款详情页由 Agent 生成替换定位 JSON 后执行：

```powershell
.venv\Scripts\python.exe main.py --source "新数据包路径" --partial-detail --replacement-map "替换定位.json"
```

- 脚本自动查找原款全平台包；没有找到时停止并要求用户提供路径。
- 用户补充路径后增加 `--original-package "原款全平台文件夹路径"` 重新执行。
- 替换定位 JSON 使用 `替换` 列表；每项包含相对于新数据包的 `新图`、相对于原款爱库存+蜂享家详情目录的 `原图`，以及原图中的 `[left, top, right, bottom]` `区域`。`操作` 可为 `替换` 或 `插入`，省略时为 `替换`；插入时 `top` 与 `bottom` 相同，表示插入线。
- JSON 还必须包含 `受影响原图` 文件名列表。它只能列出确实被某个替换项修改的原款长图，并须与 `替换` 中出现的全部 `原图` 完全一致。

脚本先在输入目录同级的临时目录生成全部内容；完成后整体发布为规定名称的优化目录，失败时不留下半成品交付目录。
